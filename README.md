# batch-review

Dispatcher and state for the `batch-review` workflow on `main`.

`candidates.json` lists the open nixpkgs pull requests that were trivial version bumps on 2026-10-19.  Each one was created after 2026-04-19, targets master, changes only version, rev, tag and hash values (plus generated lock files), has at most 100 rebuilds, and had no nixpkgs-review-gha result.

Each workflow run executes `dispatch.py` for up to about five hours.  It dispatches `review.yml` for the next candidates, newest first, on x86_64-linux, aarch64-linux and aarch64-darwin (sandbox = true) with on-success = approve, and checks each pull request again just before dispatching it.  GitHub Pro runs 40 jobs at a time, but only 5 on macOS.  The dispatcher keeps review runs within 36 jobs in total, counting 3 for a review with aarch64-darwin and 2 without, and keeps at most 8 Darwin reviews in flight.  A pull request whose `10.rebuild-darwin` label is 0 is reviewed without aarch64-darwin, and such Linux-only reviews keep going while the Darwin cap is full.  At most 10 reviews may have run for more than 90 minutes, usually large rebuilds.  A review still running after 4 hours is cancelled, since few finish before GitHub's 6-hour job limit and they hold runners that other reviews need.  `state.json` records every dispatched or skipped pull request and is committed back to this branch every 30 minutes and at the end of the run.  When a run ends, it starts the next one, and an hourly schedule restarts the chain if it ever breaks.

GitHub often has no macOS arm64 runner to spare during US working hours, roughly 13:00 to 21:00 UTC.  The aarch64-darwin job then fails after about 15 minutes without starting, and the review posts nothing.  Once these failures stop, the dispatcher re-runs only the failed jobs of such a review, which keeps its Linux results, provided that the head of the pull request is unchanged.  Otherwise it checks the pull request again and dispatches a new review.  It makes up to 8 attempts, waiting 30 minutes after the first failure and twice as long after each further one, up to 4 hours.  While the failures are recent, it keeps at most 3 batch reviews in flight.  Reviews that fail for other reasons, such as the 6-hour job limit or a lost runner, are recorded as final in `state.json` and are not retried.

To pause, run `gh workflow disable batch-review.yml -R yzhou216/nixpkgs-review-gha`.  The running dispatcher stops within about two minutes and does not start another run.  To resume, run `gh workflow enable batch-review.yml -R yzhou216/nixpkgs-review-gha` followed by `gh workflow run batch-review.yml -R yzhou216/nixpkgs-review-gha`.  The dispatcher disables the workflow itself once every candidate has been handled.

Since 2026-10-24, r-ryantm's pull requests get their results as comments without an approval.  pbsds asked on #550000 for no automated approvals of them, but said that the results are useful, since r-ryantm only builds on x86_64-linux.  Such a pull request is skipped only when a nixpkgs-review-gha result for its current head exists, whoever posted it, and its review needs no triviality check.  `state.json` can also hold re-reviews of updated pull requests that are not candidates, such as the user's own, with an `on_success` of `nothing`; the dispatcher tracks and re-runs them like any other review.  Records with the status `requeue` go first, newest first.

On 2026-10-30, every open r-ryantm pull request on master without a result for its current head was queued as a `requeue` record, 629 in all.  Left out were drafts, pull requests with more than 100 rebuilds or a merge conflict, and 39 that hit the 4-hour cutoff or the 6-hour job limit at the same head before.  Superseded ones were closed instead.  The dispatcher reviews a pull request with `--eval local` when the comparison artifact of its CI evaluation has expired, and dispatches no review of a pull request that the fork is still reviewing.
